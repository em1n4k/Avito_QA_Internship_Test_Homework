# Тест-кейс

## **Тестируемый модуль:** API для работы с пользователями, объявлениями и статистикой.

## **Тестовый стенд:** `https://qa-internship.avito.com`

## **Документация:** условия задания и Postman-коллекция.

## Общие предусловия

- Тестовый стенд доступен;
- Для новых пользователей используются уникальные `username`;
- Запросы с телом JSON отправляются с заголовком `Content-Type: application/json`;
- Для защищённых запросов используется заголовок `Authorization: Bearer <accessToken>` с токеном, полученным при авторизации, если в тест-кейсе не указано иное.

## 1. Регистрация — `POST /api/1/register`

Тело запросов регистрации и авторизации содержит `username` и `password` (Здесь токены НЕ требуются)

| ID | Название | Предусловия | Шаги | Ожидаемый результат                                          |
| --- | --- | --- | --- |--------------------------------------------------------------|
| TC-01 | Регистрация нового пользователя | Пользователя с таким именем нет | Отправить POST с новым username и корректным password без токена | HTTP 201; Возвращается числовой `id` и переданный `username` |
| TC-02 | Повторная регистрация | Пользователь уже зарегистрирован | Отправить POST с теми же username и password | HTTP 409; Повторная регистрация отклонена                    |
| TC-03 | Пустое имя или пароль | Подготовлены корректные данные | Отправить два отдельных запроса: с пустым username и с пустым password. Второе поле оставить корректным | HTTP 400 в обоих случаях                                     |
| TC-04 | Не передано имя или пароль | Подготовлены корректные данные | Отправить два отдельных запроса: без username и без password, оставляя другое поле корректным | HTTP 400 в обоих случаях                                     |

## 3. Создание объявления — `POST /api/1/item`

Пример корректного тела запроса (JSON):

```json
{
    "sellerID": 123,
    "name": "testItem",
    "price": 9900,
    "statistics": {
        "likes": 21,
        "viewCount": 11,
        "contacts": 43
    }
}
```

Вместо `123` подставляем ID зарегистрированного пользователя. Эти значения цены и статистики используются в тестах, если не указано другое

- Ограничения цены, названия и счётчиков не описаны; 
- Для TC-14–TC-18 ожидаемые правила являются предположениями; Допустимы HTTP 200 с сохранением переданных данных либо HTTP 400 без создания объявления; 
- Ошибок 5xx быть не должно; 
- допустимость самих значений требует уточнения;

| ID | Название | Предусловия | Шаги                                                                                                                                                         | Ожидаемый результат                                                                                                                                  |
| --- | --- | --- |--------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| TC-09 | Создание объявления | Пользователь зарегистрирован и авторизован | 1. Отправить POST с корректными данными; 2. Взять UUID из status; 3. Получить объявление по UUID                                                             | POST — 200, возвращён корректный UUID; GET — 200, ID, sellerID, название, цена и статистика совпадают с созданными данными                           |
| TC-10 | Два одинаковых объявления | Пользователь авторизован | Дважды отправить POST с одинаковыми данными. UUID разные, остальные данные совпадают с отправленными                                                                        |
| TC-11 | Создание с чужим sellerID | Созданы и авторизованы два пользователя A и B | С токеном A отправить POST с ID продавца B. Проверить список объявлений B его токеном                                                                        | HTTP 400 или 401. В списке B новое объявление не появилось                                                                                           |
| TC-12 | Подмена пользователя через X-UserId | Созданы и авторизованы A и B | С токеном A и заголовком `X-UserId` со значением ID пользователя B отправить POST сначала с sellerID B, затем с sellerID A. Проверить списки обоих продавцов | Первый запрос — 400 или 401; Второй — 200 с созданием объявления только у A либо 400/401 без создания; Заголовок не позволяет действовать от имени B |
| TC-13 | Неверный тип данных | Пользователь авторизован | Отправить отдельные запросы с `price: "abc"` и `statistics: "invalid"`. | TC-14 | Пустое название | Пользователь авторизован | Отправить POST с `name: ""`                                                                                                                                  | Предположение: HTTP 400 без создания объявления; при 200 проверить сохранённое значение                                                              |
| TC-15 | Счётчики равны 0 и 1 | Пользователь авторизован | Отправить два POST: все счётчики равны 0, затем все равны 1. При успехе получить объявления                                                                  | Предположение: HTTP 200 при создании и чтении, счётчики совпадают с переданными                                                                      |
| TC-16 | Отрицательная статистика | Пользователь авторизован | По очереди установить likes, viewCount и contacts в -1. | TC-18 | Цена 0 и 1 | Пользователь авторизован | Отдельно отправить POST с `price: 0` и `price: 1`. При успехе получить объявление                                                                            | Предположение: для 1 — HTTP 200 и цена сохранена. Для 0 допустимость неизвестна: ожидаем 200 с сохранением цены либо 400 без создания                |

## 8. Доступ к защищённым ручкам

- Для TC-29 и TC-30 проверяем все шесть запросов по отдельности; 
- Для каждого варианта создаём свои данные; 
- В POST передаём корректное тело, в остальных запросах — корректные ID; 
- После POST проверяем, что новое объявление не появилось, после DELETE — что исходное объявление осталось; 
- Для проверки состояния после запроса используем действительный токен;

| Метод | Endpoint |
| --- | --- |
| POST | `/api/1/item` |
| GET | `/api/1/item/{id}` |
| GET | `/api/1/{sellerID}/item` |
| GET | `/api/1/statistic/{id}` |
| GET | `/api/2/statistic/{id}` |
| DELETE | `/api/2/item/{id}` |

| ID | Название | Предусловия | Шаги                                                                                                                | Ожидаемый результат                                                          |
| --- | --- | --- |---------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------|
| TC-29 | Запрос без токена | Пользователь авторизован, объявление создано | Отправить каждый из шести запросов без заголовка Authorization; Проверить состояние объявления и списка             | HTTP 401; Данные не выданы, новые объявления не созданы, исходное не удалено |
| TC-30 | Запрос с неверным токеном | Пользователь авторизован, объявление создано | Отправить каждый из шести запросов с `Authorization: Bearer invalid-token`. Проверить состояние объявления и списка | HTTP 401; Данные не выданы, новые объявления не созданы, исходное не удалено |

## Техники тест-дизайна

- Классы эквивалентности — правильные и неправильные данные, существующие и несуществующие ID;
- Анализ граничных значений — цена и счётчики: -1, 0, 1 около предполагаемой нижней границы;
- Проверка сочетаний условий — наличие и валидность токена, совпадение sellerID с ID пользователя;
- Предугадывание ошибок — пропущенные поля, пустые строки, неверные типы данных;
- Переходы состояний — создание, удаление и повторное получение объявления.
